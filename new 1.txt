# Enterprise Security Audit Logging Framework

## 1. Objective

Design and implement an enterprise-grade **Security Audit Logging Framework** for Spring Boot applications using **Java 21**.

The framework is intended for **security auditing and compliance**.

It shall capture **who performed which business action on which business data**, while integrating seamlessly with the organization's existing Enterprise Logging Framework (EFK).

The framework is intended solely for security audit logging and shall not replace application logging used for troubleshooting or diagnostics.

---

# 2. Technology Stack

- Java 21
- Spring Boot 3.x
- Spring MVC
- HandlerInterceptor
- Jackson
- SLF4J
- Logback
- MDC (Mapped Diagnostic Context)

Do not use Lombok - Use explicit constructors, getters and setters.

---

# 3. Existing Enterprise Logging Standard

The application already follows the enterprise Logback pattern.

The framework shall **not modify** the existing logging format.

```text
[%d{yyyy-MM-dd'T'HH:mm:ss.SSS+08:00}]
[%p]
[%-50c]
[%X{traceId}]
[%X{contextId}]
[APM000119]
[%X{bizFunc}]
[%X{messageType}]
[1.0.0.0]
[%-20t]
[%X{bizKeys}]
[%m]
```

The framework shall populate the required MDC values only.

---

# 4. Scope

The framework shall audit **Controller requests only**.

The framework shall not audit

- Service layer
- Repository layer
- DAO layer
- SQL statements
- External REST calls
- Internal application execution

The purpose is to record user business activities for audit and compliance.

---

# 5. Security Audit Annotation

Controllers shall declare audit metadata using a custom annotation.

Example

```java
@SecurityAudit(
    module = AuditModule.AGENCY_INQUIRY,
    action = AuditAction.ENQUIRY
)
```

Controllers shall not manually

- write audit logs
- populate MDC
- build audit events

---

# 6. Audit Lifecycle

Each audited request shall generate exactly two audit logs.

## Enter Log

Generated immediately before Controller execution.

```
Enter approveClaim()
```

## Exit Log (Success)

Generated after successful execution.

```
Exit approveClaim()
```

## Exit Log (Failure)

Generated when an exception occurs.

```
Exit approveClaim() - FAILED
```

---

# 7. MDC

The framework shall populate

## traceId

Request Trace Identifier. (Alphanumeric of 10 characters)

## contextId

Request Context Identifier. (Alphanumeric of 5 characters)

## messageType

Always

```
SecurityAudit
```

## bizFunc

Business operation derived from the annotation.

Examples

- LOGIN
- LOGOUT
- SEARCH
- CREATE
- UPDATE
- DELETE

## bizKeys

`bizKeys` shall contain a **single JSON string** describing the audited business context.

The JSON schema shall remain consistent across all applications.

It shall contain business information only.

IP address and userId is mandatory. 

Example

```json
{
  "userId":"KAI001",
  "clientIp":"10.10.10.10",
  "agencyCode": "AGY001", 
}
```

Success

```json
{
  "userId":"KAI001",
  "clientIp":"10.10.10.10",
  "agencyCode": "AGY001", 
  "result":"SUCCESS"
}
```

Failure

```json
{
  "userId":"KAI001",
  "clientIp":"10.10.10.10",
  "agencyCode": "AGY001", 
  "result":"FAILED",
  "errorCode":"CLAIM001",
  "errorMessage":"Validation failed"
}
```

---

# 8. bizKeys Rules

`bizKeys` shall contain business information only.

It shall never contain

- traceId
- contextId
- logger name
- thread name
- log level
- execution duration
- Enter
- Exit

Null values shall not be serialized.

The JSON structure shall remain consistent across all applications.

---

# 9. Module-based Business Field Configuration

The framework shall support module-specific business field configuration.

The module shall be determined from the `@SecurityAudit` annotation.

Example

```java
@SecurityAudit(
    module = AuditModule.AGENCY_INQUIRY,
    action = AuditAction.ENQUIRY
)
```

Business fields shall be configurable through:

- application.yml
- @ConfigurationProperties

## Initial Configuration

To simplify framework adoption, the framework shall automatically discover business fields associated with each module and generate an initial configuration.

The generated configuration shall explicitly list every discovered field.

Example

```yaml
security-audit:

  modules:

    AGENCY_INQUIRY:
      business-fields:
        - agency_code
        - agency_name

    AGENT_INQUIRY:
      business-fields:
        - agent_code
        - agent_name
```

The framework shall not generate wildcard (`*`) configurations.

## Developer Responsibility

The generated configuration serves as the initial baseline.

Application developers shall review the generated configuration and remove fields that are not required for auditing.

Example

Before review

```yaml
AGENCY_INQUIRY:
    business-fields:
      - agency_code
      - agency_name
```

After review

```yaml
CLAIM:
  business-fields:
    - agency_code
```

## Framework Behaviour

Only configured fields shall be serialized into `bizKeys`.

Fields removed from the configuration shall not be logged.

If a configured field does not exist in the request, it shall be silently ignored.

No exception or warning shall be generated.

---

# 10. PII Protection

The framework shall prevent Personally Identifiable Information (PII) from being written into Security Audit logs.

PII masking shall occur after business field extraction and before JSON serialization.

## Default PII Detection

The framework shall provide configurable PII field patterns instead of fixed field names.

Default patterns shall include:

```yaml
security-audit:

  pii-patterns:

    - "*PolicyNo"
    - "*PolicyNumber"

    - "*Name"
    - "*FullName"
    - "*CustomerName"
    - "*InsuredName"

    - "*ContactNo"
    - "*ContactNumber"
    - "*PhoneNo"
    - "*MobileNo"

    - "*Email"
    - "*EmailAddress"
```

These patterns are intended to identify business information such as:

- Policy Number
- Person Name
- Contact Number
- Email Address

Applications may extend or override these patterns.

## Example

Before masking

```json
{
  "policyNo":"PL123456789",
  "insuredName":"John Tan",
  "contactNumber":"0123456789",
  "emailAddress":"john.tan@company.com"
}
```

After masking

```json
{
  "policyNo":"PL12345****",
  "insuredName":"J*** T**",
  "contactNumber":"012****789",
  "emailAddress":"j***.tan@company.com"
}
```

## Framework Behaviour

If a configured business field matches a configured PII pattern:

- the field shall remain in `bizKeys`;
- the value shall be masked before serialization;
- the original value shall never be written to the audit log.

Masking logic shall be centralized to ensure consistent behaviour across all applications.

---

# 11. JSON Serialization

The framework shall serialize audit events using Jackson.

Manual JSON string concatenation shall not be used.

Null values shall be omitted.

---

# 12. MDC Lifecycle

Before Controller execution

- Populate MDC
- Build audit event
- Generate Enter log

After Controller execution

- Generate Exit log
- Clear MDC

MDC shall never leak between requests.

---

# 13. Performance

The implementation shall

- minimize object creation;
- avoid unnecessary reflection;
- avoid request body logging;
- avoid repeated JSON serialization;
- support high concurrency; and
- minimize request latency.

---

# 14. Design Principles

Follow

- SOLID
- Single Responsibility Principle
- Open/Closed Principle
- Separation of Concerns

The interceptor shall coordinate the audit process only.

Business field discovery, extraction, masking, serialization and logging shall be implemented in dedicated components.

# 17. Expected Outcome

The resulting framework shall

- integrate with the existing enterprise EFK logging standard;
- standardize Security Audit logging across all Spring Boot services;
- require only the `@SecurityAudit` annotation on Controller methods;
- keep Controllers free from audit logging implementation;
- automatically generate an initial module configuration listing all discovered business fields;
- allow developers to refine the allowlist by removing unnecessary fields;
- automatically detect and mask common PII using configurable field patterns;
- centralize all audit logic within the framework;
- serialize business context consistently into `bizKeys`;
- require no framework code changes when new business fields or modules are introduced;
- remain reusable, configurable and extensible across multiple enterprise applications.
